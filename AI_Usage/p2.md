# AI Usage: Distributed Probe Agent

Anurag planned the P2 probe-agent work on his own and then used AI assistance to get implementation guidance for the agent. The AI prompts were used sequentially to build the standalone distributed probe agent. The implementation was verified manually by him later.

AI was also used to initially generate parts of the project report. The generated report text was manually verified against the code, manually rewritten for clarity and consistency, and the PPT was prepared manually.

P2 was responsible for the agent side of the project, not the Kubernetes controller. The important files for this part were:

```text
cmd/agent/main.go
pkg/server.go
pkg/prober.go
pkg/contract/types.go
Dockerfile.agent
config/agent/daemonset.yaml
```

## Prompt 1: Agent Skeleton

```text
Implement P2, the standalone distributed probe agent, in the existing Go repo.

Use this exact file structure:
- cmd/agent/main.go for the binary entry point
- pkg/server.go for the HTTP/control server and TCP data listener
- pkg/prober.go for probe option parsing and probe execution
- pkg/contract/types.go only for the shared ProbeResult contract if it already exists

Do not introduce Kubernetes controller code. This is only the agent.

Create an agent server with two separate listeners:
- control HTTP listener on :8080
- data TCP listener on :9376

The split is mandatory because control-channel failure must be distinguishable from data-plane failure. The main function should start the agent cleanly and log startup.
```

## Prompt 2: Health Endpoint

```text
Extend the P2 agent server with GET /healthz.

It should return JSON with:
- status: "ok"
- nodeName from NODE_NAME env var, fallback "localhost"
- podIP from POD_IP env var, fallback "127.0.0.1"

Keep this in pkg/server.go. Use only Go standard library packages unless the repo already uses something else. The endpoint must work locally with go run ./cmd/agent.
```

## Prompt 3: Probe Option Parser

```text
Implement probe request parsing in pkg/prober.go.

Create a ProbeOptions struct with:
- Target string
- Timeout time.Duration
- Count int
- PayloadBytes int
- ProbeType string, or keep the repo's existing field name if already present

Parse these query parameters:
- target, required
- timeout, default 2s
- count, default 1 or 5 if the surrounding code expects it
- payloadBytes, default 1024
- type, default tcp

If target has no port, default it to port 9376. Return a clear error when target is missing. Keep behavior compatible with /probe?target=<ip>:<port>&timeout=<dur>&count=<n>.
```

## Prompt 4: TCP Data Listener

```text
Implement the data-plane listener in pkg/server.go.

The listener must bind :9376 and accept TCP connections concurrently. For each connection:
- set a short deadline
- read/discard or safely close the connection
- never crash the whole server on an individual accept/connection error

This listener represents the real pod-to-pod data-plane target that other agents dial.
```

## Prompt 5: TCP Probe Execution

```text
Implement ExecuteProbe in pkg/prober.go.

For TCP mode:
- run Count dial attempts to Target using net.DialTimeout
- send PayloadBytes bytes when connected
- record successful probes, failed probes, average RTT in milliseconds, min/max RTT, jitter, burst loss, bytes sent, durationMillis, and throughput/bandwidth
- return contract.ProbeResult

Use this success rule:
- Success is true if at least one probe succeeds and lossRate is less than 1.0
- LossRate = failed / count
- AgentError must be false for data-plane dial failures
- AgentError should only be true when the control request itself fails or the probe request cannot be parsed/cancelled
```

## Prompt 6: Probe Endpoint

```text
Wire GET /probe in pkg/server.go.

Behavior:
- parse query params with ParseProbeOptions
- on bad request, return HTTP 400 JSON compatible with contract.ProbeResult:
  success=false, lossRate=1.0, error=<message>, agentError=true
- otherwise call ExecuteProbe with the request context
- return HTTP 200 JSON contract.ProbeResult

Keep the JSON field names compatible with pkg/contract/types.go, especially success, lossRate, rttMillis, error, and agentError.
```

## Prompt 7: Metrics Endpoint

```text
Add a simple GET /metrics endpoint to the agent server.

At minimum expose Prometheus-style text:
- netprobe_agent_up 1

If easy, add lightweight agent-local counters for probe requests and probe failures, but do not overbuild this. The operator-side metrics can remain separate.
```

## Prompt 8: Container and DaemonSet Wiring

```text
Add or update the P2 deployment files for the agent.

Dockerfile.agent should:
- build ./cmd/agent
- copy pkg/ and contract code needed by the agent
- expose 8080 and 9376
- run the compiled agent binary

config/agent/daemonset.yaml should:
- create a DaemonSet named netprobe-agent
- run in namespace netprobe-system
- use label app=netprobe-agent
- set hostNetwork: false
- expose ports 8080 named control and 9376 named data
- inject NODE_NAME from spec.nodeName
- inject POD_IP from status.podIP
- add a /healthz liveness probe
- set small CPU/memory requests and limits

Do not give extra privileges for TCP mode. Only add NET_RAW later if ICMP mode is implemented.
```

## Prompt 9: Local Verification

```text
Add focused tests or a short verification guide for P2.

Verify:
- /healthz works outside Kubernetes
- /probe rejects a missing target with agentError=true
- TCP probe against a local listener succeeds
- TCP probe against an unreachable address returns success=false, lossRate=1.0, agentError=false
- JSON matches contract.ProbeResult
- two local agent instances can probe each other's data ports when configured on different ports or run in containers

Keep the implementation independent from the operator and CRD.
```

## Note

The original plan mentioned `cmd/agent/` and `pkg/agent/`, but Anurag's actual repo design used `cmd/agent/` with root-level `pkg/server.go` and `pkg/prober.go`. These prompts intentionally followed the current repository structure.
